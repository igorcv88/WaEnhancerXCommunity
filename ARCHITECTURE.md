# Architecture

## Base and identity

WaEnhancer Community is an independent GPLv3 fork based on the upstream WaEnhancer stable 1.7.0 line. Later upstream code is treated as a reference source and ported selectively when it fits the Community architecture.

The installed application ID is `com.waenhancer.community`. The Java package/Android namespace remains `com.waenhancer` where changing it would add compatibility risk without changing the installed identity.

## Runtime model

The project runs in two main contexts:

- the standalone module application, which owns settings, local UI, backups, updates, migrations, diagnostics, and private storage;
- the injected WhatsApp or WhatsApp Business process, which resolves and installs approved hooks and reads only the configuration needed by those hooks.

Executable module code is built from this repository. The Community fork does not depend on a closed-source Helper APK, an external DEX, or an externally loaded native library for its feature runtime.

## Preferences and storage

`PreferenceSchema` is the source of truth for preference type, storage class, sensitivity, exportability, defaults, and bounds.

There are two preference domains:

- the public/default store contains non-secret configuration that the hooked process must read through the cross-process preference bridge;
- `private_config` is `MODE_PRIVATE` and contains secrets, migration state, updater internals, caches, and other module-only state.

A hook that needs a secret obtains it through a narrow provider operation rather than by placing the secret in the public store. `SafePrefs` and the provider-backed preference bridge are used when the hooked process must safely propagate a state change back to the module process.

Private databases/files hold `Deleted for Me` records, preserved media, migration snapshots, and local diagnostics.

### User-selected WhatsApp emoji fonts

The companion app's document picker accepts a user-provided color emoji SFNT/TTF (up to 128 MB), verifies the bounded table directory and that Android can load the font, then atomically replaces one fixed file inside its private `files/user-emoji/` directory. The source document URI is not retained; the original document is not altered. Only a non-exported display-name cache key lives in `private_config`, and the font binary is deliberately omitted from application backups and releases. No Apple or third-party emoji artwork is shipped with the module.

The existing UID-authenticated HookBinder exposes exactly one new read-only capability, `openEmojiFont()`. It takes no path and returns a descriptor for the fixed private font, using `O_NOFOLLOW` and a regular-file check. The general file bridge still refuses private paths. When the user's **Disable Default Emojis** preference is enabled, the WhatsApp-side hook starts a one-time asynchronous `Typeface` load from that descriptor so Binder delays never block application startup or draw frames. Lite Mode deliberately does not initialize the shared `WppCore` bridge; font loading can instead establish one temporary `ProviderClient` connection for this read-only call without enabling the global bridge. Intercepted emoji-only spans are painted with a cloned `Paint` and that typeface once available, without mutating the sender's paint or changing Android's font fallback configuration. The initial One UI 9 physical test showed a loaded font and 16 installed draw hooks, but no emoji draw interceptions across three WhatsApp process launches. An additional fallback intercepts insertion of emoji-only `ReplacementSpan` objects into Android `Spannable` text and substitutes a `TypefaceSpan` for the user-selected font, preserving all non-emoji spans. If the TTF is still loading, the original WhatsApp span stays in place and is queued as weak references (at most 256). After a successful load, a main-thread task replaces still-attached, still-emoji-only queued spans and notifies their span watchers. A failed/missing TTF leaves WhatsApp's original spans intact. Bounded class/length diagnostics and one-time deferred/applied markers never log message content. WhatsApp may copy spans to other text buffers, and entries past the queue limit are not retroactively rewritten; those cases still require device validation. Reopening WhatsApp is required after an import/removal. Hooks and rendering remain version-specific and require another physical test.

## IPC and automation

Cross-process entry points use capability-specific contracts rather than generic storage access.

- `HookProvider` exposes schema-approved configuration and validates callers before privileged operations.
- `DeletedMessagesProvider` exposes only the deleted-message/media operations it needs and validates callers on every operation.
- exported activities/services that must be launched from the hooked process are explicit and documented.
- Tasker message sending is disabled by default and protected by a per-installation secret, rate limiting, deduplication, and an optional package allowlist. A broadcast does not provide trustworthy sender identity, so the token is the security boundary and the declared package is defense in depth.

The application-only runtime obtains its file-operation Binder directly from `HookProvider`. There is no SettingsProvider relay, exported BridgeService, PackageManager visibility hook, update-session interception or OS downgrade hook. UID authentication is repeated for every Binder file transaction as well as provider acquisition. File access is limited to canonical primary shared-storage media outputs and read-only theme/selected-wallpaper images; private paths, traversal and enumeration are refused, and opened descriptors are revalidated before truncation/return. Preference bridge writes/removes are public-only and schema-type-checked; private embedded controls open the companion editor. `android:forceQueryable` and explicit module authorities remain; physical API-37 visibility must be verified. `initZygote` stores only the module path. Stale out-of-scope load callbacks return before hook registration or application-helper initialization. Optional bootloader/anti-detector spoof code and controls are removed; legacy stored preferences remain for rollback.

## Hook loading and compatibility

WhatsApp internals are version-sensitive. Resolvers must fail closed for the affected feature rather than turn a missing method or field into a process-wide crash.

The runtime diagnostics layer records resolver/install/trigger evidence without collecting message content. `ValidationSession` lets the user explicitly run a local functional validation session against WhatsApp or WhatsApp Business and preview/copy the result.

Compatibility evidence is scoped to the installed WhatsApp build and module build.

`UnobfuscatorCache` persists DexKit results as string descriptors invalidated by WhatsApp version code, module update time/version name and a cache schema stamp. A descriptor that no longer decodes, or whose member return/field type changed, is evicted and resolved once more; resolution runs under the same `Unobfuscator.class` monitor as the static synchronized loaders (one reentrant monitor, so nested loaders cannot deadlock), while valid persisted descriptors decode without locking; failures are negative-cached for the process lifetime (bounded) and cleared only by the explicit clear-cache broadcast or a new process. Upstream-derived resolver fallbacks must keep a unique legacy match first and accept a new anchor only when it is unambiguous. Absence of evidence must not be promoted to a false incompatibility claim.

The injected `MessageHistory` SQLite store treats `viewed` as explicit receipt-release authorization. Its DB/cache operations are serialized so delayed privacy callbacks cannot revoke that authorization. Known legacy message-key schemas (versions 4–6) migrate to version 7 transactionally while retaining original receipt rows in an archive table. Unmapped row-ID schemas and unknown downgrades preserve their source files; they require a validated migration before their old history can become active.

## Themes and visual customization

The visual stack has three separate responsibilities:

- `SemanticTheme` derives semantic color tokens from presets/accent colors with contrast safeguards;
- `CssSafetyManager` validates user CSS, limits size/image references, provides temporary testing, last-known-good rollback, and safe mode;
- `GlassSpec`/`GlassRenderer`/`GlassSurface` implement open glass materials. Liquid Glass is applied selectively to surfaces whose backdrop and performance justify it rather than as a global effect.

Live app-surface glass uses `GlassPane` (ported from WaThemer): a view inserted beneath the surface, never a replacement of the surface's background. Each pane records only the region behind itself on the GPU, from a named source subtree (such as the message list) over its wallpaper underlay, and `LiquidLens` refracts and blurs that recording. `GlassPaneGraph` refuses any source that contains the pane, directly or through another pane: a recording that reaches its own pane is a display-list cycle that crashes HWUI's RenderThread natively, outside any Java error handling. In the conversation screen the header and footer float over the list, which is padded with `clipToPadding=false`; every layout change is recorded and restored when the surface is switched off. Every other surface uses `GlassMaterialDrawable` in its own background slot, made live by `BehindRecorder`: it records only what the window draws beneath that view (ancestors' backgrounds and the siblings drawn before its branch, by Z then index), never the view or anything after it, so no two surfaces can record each other. Both paths share `LiveBackdrop` (a GPU display-list recording, `LiquidLens` as a `RenderEffect`). As of PR #102's 2026-10-30 stability follow-up, neither pane nor drawable paints `GlassSpec.neutralFallback` when a safe recording is missing: it draws no glass pixels until recapture. This prevents the historical tinted slab, without retaining pixels from a different chat/source epoch. The old `GlassSpec` fallback API remains for non-live materials and tests but is not a substitute in these live providers. Battery Saver does not disable intra-window HWUI/AGSL optics. The legacy recording scales the display list by 1/4 and back; that does not lower the rasterisation resolution and only adds a rounding error, so it must not be described as a downsample.

Optical corrections are a second renderer behind `GlassOptics`. The user switches them in the Liquid Glass page, `config.LiquidGlassOptics` stores them, and `AppLiquidGlass` publishes them on every resume; every provider (panes, drawables, the floating bar's `GlassSurface`) compares `GlassOptics.revision()` and rebuilds its effect on the next frame. They are off by default; off is the legacy shader, capture scale and scheduling logic (the scheduling now lives in shared classes, so the logic is the same but the code paths are not literally identical).

Stable geometry is an invariant of the corrected renderer, not a switch: a bounded, fold-free warp (`LensModel` mirrors the shader; `LensJacobianTest` requires σ_min ≥ 0.30 per channel, measured 0.335 with the amplitude cap at 0.33 of the bevel), 1:1 recording, and exact `transformMatrixToGlobal` placement. The folding legacy warp is reachable only as a diagnostic view. Four groups can be switched independently:
- **Filtering.** A platform blur low-pass mixed with the sharp input by depth, through a two-pass `RenderEffect` graph in `LensEffect`. Each pass carries its own share (soft β, sharp 1−β), including coverage, and the passes are added (`BlendMode.PLUS`), so coverage is applied exactly once. The recording is padded by three requested blur radii, and `BehindRecorder.paintExact` culls siblings against that padded rect and draws them in Z order.
- **Adaptive contrast.** It needs filtering. In-shader protection toward a contrast target, applied last, after lighting, in linear light, in both passes. The historical graph adds encoded branch colours; linear-luminance model tests are not evidence of the final GPU mixture. The target is the theme's content colour; grey hint and secondary icons are not guaranteed.
- **Colour.** Linear light, `layout(color)` uniforms, and calibrated saturation, dispersion and highlights.
- **Temporal.** Damage-driven capture (`CaptureScheduler`): no periodic heartbeat, one trailing frame at rest. Effects keyed on full material equality. Interaction state kept across material changes. A per-window `LiveBudget` in effective pixel-passes (padded area × passes) that admits panes and drawables alike. Admission is sticky: a live surface keeps its slot while visible, and only new surfaces can be refused, so layout changes cannot flip surfaces between live and unavailable presentation. The default OneMate material uses this persistent budget/scheduler even when the experimental classic temporal switch is off.

The corrections change optics and scheduling only, never what may be recorded: the acyclicity guards (`GlassPaneGraph`, `BehindRecorder`) are shared by both renderers. If a device refuses to compile the corrected program, or it fails three times, surfaces drop back to the legacy lens; a native RenderThread failure is outside what this can catch.

Activity stop suspends app-glass observers and owned callbacks while retaining view bindings and conversation layout. `ENDED` retains its historical stop meaning for other features; `DESTROYED` is a separate callback and disposes the session. Capture pixels are discarded across visibility/source/geometry epochs and recaptured before drawing on resume. Conversation panes resolve material from their own root/session, not a global foreground material. A capture publishes `hasContent` only after recording and effect installation complete; partial recordings cannot be presented.

`SurfaceRecovery` bounds the retry rate rather than the total number of transient attempts. After 16/64 ms retries, repeated transient failures enter `BACKOFF` with 1/2/4/5-second waits, capped at 5 seconds, so a stable source can recover without another lifecycle/layout event. Owned callbacks are cancelled during suspension/destruction; the session preserves later retry deadlines when an earlier surface retries. Capability/linkage failure stays disabled. `RecordingState` distinguishes uninitialized, recorded, unexpectedly dropped, intentionally released, budget refused and temporarily unavailable pixels. Only an eligible unexpected drop requests immediate redraw; a due transient retry captures without forcing another frame. Missing/unsafe live content results in transparency (no static slab and no potentially stale conversation pixels). `GlassPaneGraph` checks sources and underlays; `BehindRecorder` keeps its ordering guard. The header has one optical capsule over a plain `WallpaperUnderlay`, and composer geometry leaves a measured 2 dp minimum gap to the native action disc in either layout direction. `GlassTrace` diagnostics record state/presentation/budget changes, opaque runtime identities, generations and rebuild counters; ordinary successful captures do not emit per-frame logs. The historical `fallbackFrames` counter now means unavailable/transparent frames on live providers, not that a fallback background was painted. Conversation panes require safe live message content: wallpaper-only content never completes their recovery, and the header re-resolves a late safe list on backoff attempts without using its coordinator as a fallback source. Resumed window epochs record each surface’s first presentation, first complete capture, first live presentation and unavailable frame count; nested capture draws do not count as presentations.

The 2026-10-09 optical calibration adds baseline/balanced/strong/reconstruction profiles, applied through the same revision/public preference boundary. Reconstruction uses a small prefilter for residual detail, a Jacobian footprint approximation, weighted linear numeric branch outputs, PLUS, and one final material/lighting/contrast/encoding pass. It does not modify the source graph or temporal recovery. LiveBudget conservatively charges 6 padded pixel-passes for reconstruction. Existing users and the floating bar's BlurView/View path retain baseline until the app-pane candidate is explicitly selected. The API33+ module-only synthetic lab exports actual hardware-rendered graphical stages through PixelCopy and a document picker, with a private cached PNG surviving configuration changes. It never reads the WhatsApp window. Requested Android blur radius is not a published Gaussian sigma. See `docs/GLASS_OPTICAL_CALIBRATION_2026-10-09.md` for the output contract and pending device acceptance.

The OneMate material (`KyantLens`, default; `liquid_glass_renderer=classic` restores the renderers above) is a third effect on the same recordings, selected by `GlassOptics.oneMate`: unchanged backdrop saturation, a 10dp blur (miuix sigma 0.45·r; OneMate uses 4dp, raised after device review), an inward-only circle-profile edge lens 24dp deep with 65% of its original displacement, a neutral black/white wash centred on 18% by the opacity slider, and a persistent narrow grazing reflection joined to a soft directional bevel. The contour has a nonzero all-angle floor and brightens with local backdrop luminance; a localized highlight responds more strongly to high-luminance media directly behind each segment. The `liquid_glass_rim_intensity` float (0–2) scales the contour and bevel, including 0 to disable illumination while preserving lens/blur. The narrow contour smoothly changes to a darker reflection target on near-white composited bodies so the edge remains visible, while the broader bevel stays luminous and the interior is unchanged. The selected-tab bubble retains its original tint and dual-light rim. App surfaces record 1:1 with a 3σ margin in `LiveBackdrop`; the floating bar installs the same effect on its BlurView. It changes no capture source, recovery or acyclicity rule; when the program is refused, the live app surface presents transparently rather than a classic static material. On the floating bar's Liquid style it replaces `LiquidMorph` with `LiquidBubble`: a pill that rises (scale 78/56, lens with depth, dispersion and inner shadow) while the selected tab is pressed, follows a drag, and selects the tab it settles on through that tab's own click. The bubble records only its preceding siblings inside the bar host (the BlurView's output and the tab row through an accent filter); the host is excluded from the BlurView's capture, so the bubble can never be inside what it records.

Non-navbar app chrome rendered by `LiveBackdrop` (including conversation composer/header and `GlassMaterialDrawable` surfaces) uses `KyantLens.appSurface`: 30dp blur, contour gain 1.8 and width 1.25dp, retaining the same neutral body, refraction and directional bevel. The `LiquidLens`/`GlassSurface` view route keeps `surface` at 10dp blur but uses contour gain 1.6 and width 1.15dp after video review showed its outline was too weak. The separate animated bubble scales its old rim highlight by 0.45, preserving lensing, blur and motion. `LiveBudget` and `LiveBackdrop` both use `appPadding` (three app-profile sigma plus one pixel). The larger padded area is charged before capture; no budget capacity increase or extra rendering pass is added. The scroll-button GlassSurface shares the view-profile contour adjustment.

The floating bottom bar has its own editor and preview but resolves shared glass material through the same rendering model. Bottom sheets can opt into glass through the shared dialog helper.

### Separate conversation chrome and message bubble glass (2026-10-30)

`liquid_glass_toolbars` controls the home/other-page toolbar resource targets and `HomeGlassChrome`. `liquid_glass_conversation_header` controls only the floating contact header in `ConversationGlassPanes`, keeping the existing message-list overlap and layout restoration. A missing conversation-header preference inherits the former toolbar value for upgrades; opening the Liquid Glass settings screen writes that inherited value so the two switches become independent. The generic toolbar binder skips descendants of `search_fragment_and_toolbar_holder` even when the contact-header switch is off.

Bubble glass keeps the historical `liquid_glass_bubbles` boolean for migration and adds the public string `liquid_glass_bubble_scope`: `off`, `outgoing`, `incoming`, or `both`. Missing scope inherits `both` only when the old boolean was on; an invalid value fails closed. `AppLiquidGlass` resolves the same direction-bearing drawable factory as `BubbleColors` (direction 3 is outgoing), and discovers the returned `GlassMaterialDrawable` whether it is a direct background or nested in a selector/layer/inset, foreground or image. The host is attached after native installation; the shared `BehindRecorder` source ordering, `LiveBudget`, material fallback and original drawable mask remain unchanged. Nested wrappers are disabled in place, without replacing the native container.

The bubble tint uses the existing `bubble_left`/`bubble_right` preferences or CSS override only when enabled. The glass optics match the composer; only an explicitly chosen bubble colour replaces the OneMate neutral wash. TextViews within the bubble owner choose black or white from the custom colour and restore their native ColorStateList when the effect is removed or a row is recycled. This is a palette-based contrast choice, not per-frame contrast measurement against moving wallpaper pixels; rich-text spans with their own foreground colour and nonstandard message layouts still require physical review. The original quoted-reply surface switch remains separate. The native factory's use, attachment route and readable text should be verified on the installed WhatsApp build before the feature is considered visually accepted.

### Shared wallpaper text bubbles (2026-11-02 prototype)

The preceding per-bubble `BehindRecorder`/factory capture description is historical. The active text-row path now uses `ConversationBackdropSource`: one isolated bitmap-only producer per screen/source epoch, prepared off the UI thread through a temporary HardwareRenderer/ImageReader. Its RenderNode contains only a borrowed native wallpaper bitmap and projection; no View/window/row is recorded. `WallpaperSnapshot` reuses the approved `WallpaperProjection` matrix without changing its native installation or underlay behavior. Only complete, uniform, supported bitmap coverage is accepted. Rows never participate in their source, and `LiveBudget` capacity for existing panes is unchanged.

`BubbleGlassDrawable` binds only after a source texture and optical shader are ready. It samples the shared, full-resolution, once-blurred texture through the existing OneMate app-profile program and a native Fyn alpha mask. Scrolling changes texture coordinates, not source revision, blur, bitmap allocation or program compilation. Native factory wrappers are pass-through except an outer factory matching the verified, already-drawn text material envelope; alpha-mask drawing bypasses that suppression. There is no transparent fallback: unsupported sources, unmeasured/recycled owners, failed shader preparation or lost texture draw/retain the native background. Producer epochs reject late asynchronous results. Suspension/destroy/wallpaper identity changes release the source and restore rows conditionally by installed drawable identity.

This first prototype supports API 33+ OneMate `conversation_row_text` with a verified Fyn mask and a safe full-coverage static bitmap wallpaper. Other message layouts, animated/unknown wallpaper, classic rendering and older Android stay native. The source admission ceiling is an estimated 128 MiB for six RGBA-buffer equivalents, without lowering resolution/blur; this is not a vendor GPU measurement. Failed preparation is not retried by a periodic loop: a source/lifecycle change can open a new epoch. The shared source key contains bitmap identity/generation, projection, output dimensions and blur radius; row offsets are excluded. Optical-only changes rebuild consumer uniforms without reblurring an unchanged source.

The native text/checks/media/touch tree is unchanged. Existing custom bubble colors and side selection remain inputs; no default blue is imposed and no appearance tuning is claimed. The approved microphone-disc palette, composer/header/recorder panes, quote foregrounds, date and wallpaper continuity are frozen. This prototype is not device acceptance or phase-C coverage: source buffer availability, final HWUI composition, native factory envelope matching, silhouette/tail and BUB-01–BUB-12 require Galaxy tests before expanding to media/audio rows.

### Voice recording and composer reply readability (PR #102 follow-up, 2026-10-30)

The resource catalog deliberately excludes `conversation_entry_action_button` and `voice_note_lock_container`: WhatsApp animates the microphone action control into a large transient circle at the start of voice recording, so a rounded generic `GlassMaterialDrawable` on it can produce a screen-sized lens. The generic QUOTES binder also excludes the animated `voice_note_draft_layout_v2` wrapper; nested quoted-message previews remain eligible. Neither surface gets a static glass fallback.

`ConversationGlassPanes` detects a visible wide voice-recording panel through its native elapsed-time label, outside `input_layout` and within the conversation footer. The same persistent composer `GlassPane` then follows the panel's geometry, and only full-bleed native backing fills are temporarily cleared. The timer, waveform, microphone animation, pause/trash/send controls and event handling remain in WhatsApp's view hierarchy. The original backgrounds are restored on exit, footer replacement and feature disable. If the native panel cannot be identified, the module leaves the recording UI native and reports structural IDs/dimensions only; it never paints a neutral/opaque fallback. This identification is a bounded heuristic and must be verified on the device before treating the voice panel as supported for this WhatsApp version.

For an in-composer reply preview, the module matches named/semantic quote containers inside the footer, applies the active glass material's content colour to sender and snippet text with separate 96%/86% alpha, and records/restores native `ColorStateList`s. This follows theme/material changes rather than sampling every wallpaper pixel; explicit foreground spans or an unknown resource tree may still require device-specific refinement. The pre-existing independent QUOTES switch still controls quote backgrounds and message-level quote surfaces.

The 2026-10-30 device trace subsequently showed that `voice_note_stub` was routed as a small 1190×115px recording region before the full 1410×414px recorder emerged roughly 1.7 seconds later. The persistent composer pane now uses the measured footer envelope from the first recognized timer, and only excludes the native action disc when it is still its ordinary small size. Native opaque full-bleed ancestors between the recorder and footer are cleared/restored while recording. The floated message-list margin is updated only when the footer's measured height changes (normal input, quoted reply, locked recording), so rows can continue under the formerly static region next to the microphone without reintroducing layout feedback loops.

The same trace recorded `bubble-factory` callbacks without any `bubble-attached` events. The factory is therefore not proof that the wrapped drawable was mounted on a row. `GlassMaterialDrawable` can now follow native `Drawable.Callback` chains when first drawn and request a deferred owner adoption. A weak per-view mapping supports callback-owned wrappers outside the ordinary background/foreground paths. Three bounded row-structure diagnostics report resource IDs and drawable class names only, not message text or media. If WhatsApp draws another copy or uses an internal Canvas path with no View callback, this route remains unproven and must fail closed rather than replacing whole message rows speculatively.

The app-chrome Kyant/OneMate profile retains 30dp blur to suppress content behind the header, with an increased inward-only refractive displacement on a 24dp rim. Its contour now screens toward white with a small tint from live local backdrop colour; the prior bright-body branch darkened the outline into grey. A new shader uniform selects this app-chrome treatment without changing the approved floating-bar profile. The conversation header also applies a weak top-to-bottom neutral wash *only after live glass was rendered*, within the same clipped `GlassPane`; it never appears during capture unavailability, creates no extra glass surface and adds no static fallback.

On the 2026-10-30 follow-up device build, native bubble-factory wrappers reported `bubble-no-host` while actual text and voice-note message rows exposed a `Fyn` native background, with a named `main_layout` child. The compatibility adapter first supported those two observed row types, and now considers other `conversation_row_*` types for media and captions only if they independently satisfy the same `Fyn` mask, bounded `main_layout`, and unambiguous horizontal-direction checks. It crops the live capture to the content bounds plus a small inset and keeps the original drawable as the alpha mask. The native row retains its layout and gestures. Row recycling may change direction and geometry; the binding reconciles them during layout. `GlassMaterialDrawable` requests a first live repaint explicitly, because successful GPU capture does not guarantee a cached Android background display list has been drawn again. Neither capture success nor forced invalidation proves that WhatsApp's later Canvas-owned bubble factory has stopped overpainting the glass; the latter still requires an on-device draw/presentation trace and visual check.

Recorder activation is now event-driven in addition to layout discovery: observed `voice_note_stub`/`voice_note_draft_layout_v2` visibility and inflation plus elapsed-time text updates request immediate synchronization of the existing composer pane and one next-frame retry. A short-lived semantic recorder signal can select the visible native stub before its timer has populated; no new pane or static material is introduced. During recording, if both the ordinary composer quote and a distinct `voice_note_draft_quoted_message_frame` are visible, the duplicate draft's alpha is temporarily zeroed and restored on exit; neither quote hierarchy nor message-reply metadata is removed. Exact hook timing and the duplicate identification still require physical verification on the installed WhatsApp version.

In the next follow-up, a native recorder can expose a short initial footer before it expands: the existing composer pane temporarily extends to a 140dp recording envelope, plus any visible quote height, and its small clipping ancestry is restored when recording ends. Semantic quote-frame discovery no longer requires two TextViews (a voice-note quote may contain only one plus a thumbnail). The native red mic indicator is aligned against the elapsed-time row only when a bounded named or positional ImageView match exists; otherwise a geometry-only diagnostic is emitted. For conversations with the glass contact header enabled, the owning Activity hides only the status bar through `WindowInsetsController`, adjusts the header margin for the cutout/safe inset and 8dp clearance, and restores its previous bar visibility/behavior and margins when the surface ends. It never sets `FLAG_FULLSCREEN`, which would disable native IME resize. Other WhatsApp screens and navigation controls retain their native state. Device acceptance is pending for the fullscreen/insets and recorder heuristics.

PR #107 device-trace follow-up (2026-10-31): `ComposerTransition` separates *presentation* from *reservation*. Every valid measured input/recorder geometry is presented in the same pre-draw by moving the one persistent composer `GlassPane` (`GlassPane.placeNow`: layout params updated, direct measure/layout without an extra traversal, and an immediate recapture for the new size); only the message-list margin/padding waits for two identical frames and 80 ms of quiet. Frames in which neither the recorder nor the input row is measurable keep the last presented pane (`HOLD`) instead of hiding it, bounded by a 700 ms bridge after which the decoration is removed and the native UI is left alone. Native recorder visibility/inflation opens one transition epoch per start/end (`signal`); timer ticks inside an epoch wake nothing. Any `GlassPane` revalidation (size, radius, source, material, visibility) recaptures on the next permitted pre-draw instead of waiting for the 33 ms rest gap, which previously presented a transparent frame. Native recorder backing fills are cleared only once the composer pane has a live recording for the current geometry (bounded retries; otherwise native backing stays). The red recording indicator is translated on both axes by `RecorderLayout.micOffset` (start side of the measured waveform, row-centred, ≥2 dp from every measured recorder control, action disc and quote; recomputed from its native translation so offsets never accumulate; restored to native when no placement fits). The quote lane is checked and reported, not moved. The conversation window no longer sets `SYSTEM_UI_FLAG_LAYOUT_STABLE`, which made legacy `fitsSystemWindows` views keep the hidden status bar's height as padding; the contact header is anchored at `max(statusBarsIgnoringVisibility, cutoutSafeTop)` + 3 dp so its screen position does not depend on that padding, and the wallpaper continuity layer moves to the decor only if content still starts below y=0. Footer decoration skips its tree walks on frames whose allocation-free native fingerprint (sizes, positions, visibility, alpha, material) and layout generation are unchanged. These are static/JVM-verified changes; device acceptance is pending.

Review audit of glass PRs #69–#105: a nested bubble wrapper replaced during recycling must be adopted in the same binding reconciliation pass (#102); an `Fyn` native message row discovered before its `main_layout` is measured must be retried after layout (#104), using weak pending-row ownership; the previous fullscreen window flag was removed (#105). `GlassPane` and `BehindRecorder` no longer subtract the drawn view's own scroll twice after applying the global placement transform (#73). The optics lab's padded synthetic recording extends test patterns into the recording margin rather than introducing a flat border into refraction calibration (#84). These repairs use the same existing glass surfaces and do not reintroduce static fallback drawing.

## Deleted data and backups

`Deleted for Me` uses a private SQLite store with incremental migrations. Preserved media is stored through a private vault with integrity metadata and quotas.

There are two backup classes:

- configuration backup is versioned and allowlisted and deliberately excludes secrets/internal state;
- full backup is portable and password-encrypted, validates the authenticated payload before mutation, includes `Deleted for Me`, schema-defined private secrets, and optional preserved media, and restores database/preferences transactionally.

Migration and restore code must preserve the source until the destination has been validated.

## Updates and releases

The app reads release metadata from `igorcv88/WaEnhancerXCommunity`. Stable and Beta are explicit channels identified by the release tag/version convention.

Downloaded APKs are verified before installation: published SHA-256, package identity, signing certificate, and version policy. Downgrades require an explicit user action.

Official releases are produced by the manually triggered GitHub Actions release workflow with JDK 21 and JVM 17 application bytecode. The workflow validates the Gradle wrapper, signs the release APK, verifies certificate/package/version metadata, calculates SHA-256, and publishes the APK directly to a GitHub Release.

For pre-merge device testing, the separate manual `Build Signed APK From Latest Open PR` workflow runs from `master`, selects the newest open, owner-authored PR from this same repository that targets `master`, and builds its immutable head SHA. It reuses the official release keystore secrets and APK identity checks, and assigns a `versionCode` one greater than the highest published stable/beta tag in the current series. The signed APK, checksum and build metadata are available only as a short-lived GitHub Actions artifact; no tag or GitHub Release is created. The workflow fails if no qualifying PR exists. It must first be merged into `master` before appearing in the Actions manual-dispatch menu.

## Invariants

- never place a secret in configuration readable by the WhatsApp process;
- never load closed executable code into the module or target process;
- no analytics or automatic remote crash reporting;
- no embedded private tokens or signing material;
- no generic exported provider operations when a narrow capability will do;
- no destructive database/preference migration fallback;
- preserve user data before tightening storage or IPC;
- isolate compatibility failures to the smallest feature possible;
- keep forward-looking work in `ROADMAP.md`; historical implementation plans belong in Git history, not in the repository root.
